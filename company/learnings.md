# Demo Co: learnings

What the company learned about operating itself, newest first. The retro loop curates it; any worker adds what surprised it. Each entry: date, what happened, the lesson, and what changed because of it (commit, loop or skill).

## Operating learnings

- **2026-11-06 · The machine was stopped twice over, and the postmortem named only one cause.** The `cos-pulse` workflow is `disabled_manually`, and the only pulses on record were started by hand (2026-11-04 01:32 UTC, 2026-11-06 20:57 UTC). The incident postmortem blamed `company/PAUSE`, but `incident` is `critical` and PAUSE never holds it. Lesson: a stale loop is first a question about the clock. Check `gh workflow list` and `pulse.json` `last_pulse` before the loop. Changed: correction appended to `company/incidents/2026-11-06-stale-incident-after-pause.md`; #8 closed with evidence; 3 agenda items cancelled because they could not fire and were redundant.
- **2026-11-06 · Resuming starts everything at once.** The first pulse after 67 h started 5 loops within 7 seconds (20:57:57 to 20:58:04 UTC). Distribution ran twice in 2 minutes: the founder's manual proof at 20:56, then a catch-up of the 09:00 slot, which the proof had already covered. Reporter replayed the 2-day-old TEST gate resume. All 5 runs ended ok in 21–83 s, so the cost was small here, but a real company with long runs would pay it in full. Changed: engine lesson under Upstream.
- **2026-11-06 · Plan usage is an account-wide reading.** The 7-day window went from 43 % (2026-11-04) to 76 % (2026-11-06), above the 75 % soft budget. All 8 loop runs on the ledger took about 6 minutes in total, so most of that usage came from other work on the founder's subscription, not from the loops. Lesson: don't cut loop cadence on this reading alone. Changed: nothing; the rule to cut cadence after 2 weeks over the soft budget stands.

- **2026-11-06 · A deliberate pause looks like an outage when the company resumes.** `company/PAUSE` ran from 2026-11-04 02:46 to 2026-11-06 21:55. The first pulse afterwards opened critical alarm #8 because the incident loop had never succeeded. Lesson: after any pause, run each loop or queue it before its `max_age_hours` runs out, counted from launch or from its last ok. Changed: backlog and retro were queued early; postmortem `company/incidents/2026-11-06-stale-incident-after-pause.md`.
- **2026-11-04 · The worker shell works after ebd1254.** Run 2611040240 ran `cos`, `git` and `gh` inside the sandbox. Before that, run 2611040234 was recorded as `ok` while it had no shell at all. Lesson: a ledger `ok` does not mean the run was healthy, so the north star count should also check that the run made tool calls. Changed: the W45 report counts that run as degraded.

## Upstream
Lessons that would help every company built with the launch-company skill (engine, loop skills, defaults). The founder's improvement routine harvests these into the skill; mark each **harvested <date>** once it has been.

- **2026-11-06 · `cos status` and the roll-up don't show that the clock is off.** The `cos-pulse` workflow was `disabled_manually`, but `cos status` still printed "next 2026-11-07 08:40" for incident, and nothing would run. Lesson: the status output and the daily roll-up should read the pulse workflow state (`gh workflow view cos-pulse.yml`) and the age of `last_pulse`, and say "clock stopped" plainly. The stale sentinel runs inside the pulse, so it cannot catch its own absence.
- **2026-11-06 · Catch-up after downtime should skip slots that were already served, and not replay stale resumes blindly.** `lastFireBetween` looks back up to 8 days. The pulse fired distribution's 09:00 slot at 20:58, after a manual distribution run at 20:56 had covered it, and it retried a 2-day-old TEST gate resume for reporter. Fix: skip a slot when `runs/<loop>.json` `last_run` is after it. Stagger a catch-up burst. Before a gate resume older than a day is retried, it should say how old it is.
- **2026-11-06 · The stale sentinel should start its clock when the clock resumed, not only after PAUSE.** This refines the incident entry below. Alarm #8 came from a gap in the pulse (the workflow was disabled), not from PAUSE: a critical loop ignores PAUSE. Use the later of `last_ok`, `launched_at` and the end of the last pulse gap or PAUSE. Then a single fix covers both kinds of stop.
- **2026-11-06 · "ok with tool calls" does not prove a healthy run (backlog B-003).** Run 2611040234 is on the ledger as `ok` with `tool_calls: 19`, and every one of those Bash calls failed ("socat not installed"). A `tool_calls > 0` rule would have counted it as clean. Lesson: count tool errors in the ledger record and mark a run whose shell calls all failed as `degraded`, or smoke-test one sandboxed Bash call before a loop starts (the 2026-11-04 entry below).
- **2026-11-06 · Record each run's own usage delta.** Ledger `usage.seven_day` is the account-wide window, so retro cannot attribute usage to loops (43 % to 76 % over two days, while the loops ran for about 6 minutes in total). Fix: read usage at the start and the end of each run, and store the delta.
- **2026-11-06 · cos-incident skill: check the clock first.** When a loop is stale, read the pulse workflow state and `last_pulse` before blaming the loop or PAUSE (see the operating entry from the same day).

- **2026-11-06 · The stale-loop sentinel should not count paused time.** In `sentinel()` (cos.mjs), `since = last_ok ?? launched_at` ignores `company/PAUSE`, so every loop that was due during a pause raises a false stale alarm on resume (alarm #8 was critical). Fix: use the later of `since` and the resume time, or give each loop one schedule period of grace after a resume. Changed: nothing upstream yet (the engine is outside worker rights).
- **2026-11-04 · The worker sandbox needs socat as well as bubblewrap.** Run 2611040233 failed without bubblewrap; after 8ac2fb5 installed it, run 2611040234 started but every Bash call failed with "socat not installed". Lesson: the GHA setup step should install `bubblewrap socat` together, and the runner should smoke-test one sandboxed Bash command before starting a loop, so a broken sandbox shows as a setup failure, not a degraded run. Changed: nothing yet (workflow is founder-owned).
